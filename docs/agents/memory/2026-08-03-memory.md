## Today's Question

Days 1–3 mapped the *architecture* of agent memory: representation, retrieval, and maintenance. But two questions have been nagging since Day 1's survey: **how do we evaluate memory quality, and can memory be attacked?** If an agent accumulates knowledge across interactions, a single adversarial memory write could steer a future consequential action (a payment, a config change, data exfiltration). Every memory system we have studied so far — MemGPT, MemoryBank, MRAgent, A-MEM, CraniMem — assumes the stored content is trustworthy. What happens when that assumption fails? And what should a memory benchmark actually measure?

## Main Paper

### Metadata

- Title: From Untrusted Input to Trusted Memory: A Systematic Study of Memory Poisoning Attacks in LLM Agents
- Authors: Pritam Dash, Tongyu Ge, Aditi Jain, Tanmay Shah, Zhiwei Shang
- Year: 2026
- Venue: arXiv (2606.04329)
- Link: https://arxiv.org/abs/2606.04329

### Why this paper?

This is the first systematic study of **memory poisoning** in LLM agents, and it lands exactly on an open question recorded in Day 1's state: "How do we prevent memory poisoning (adversarial content injected into memory that later influences critical decisions)?" It also connects the memory course to the safety thread already established in the tool-use topic (ChainCaps, ToolPrivBench, ChainFuzzer): there, the danger was unsafe *tool composition*; here, the danger is unsafe *memory composition* — individually benign memories that combine into a harmful decision. It is a survey-like, taxonomizing paper (right for map-building) and it ships a benchmark (MPBench), which lets it double as the evaluation dimension of this topic.

### Core Problem

Persistent memory is what makes agents useful over long horizons — but it is also a **persistent attack surface**. The paper identifies the fundamental asymmetry:

- In a single session, an LLM can defend against prompt injection because the untrusted content stays visible and bounded.
- In a memory-augmented agent, untrusted content written into memory in **session A** gets retrieved **sessions later** and is treated as trusted internal state. The adversarial content has already "passed" the input gate by the time it influences a decision.

The attack surface is broad because modern agents write to memory from **four channels**: (1) user messages, (2) tool outputs, (3) retrieved documents/web content, and (4) the agent's own reasoning traces. Any of these can carry poisoned content into long-term storage.

### Main Idea

The paper contributes three things, in increasing order of generality:

1. **Four memory write channels** — the paths through which untrusted content can enter persistent memory (user input, tool output, retrieved content, self-generated traces).

2. **Nine structural vulnerabilities** — properties of model capabilities, system-prompt design, and agent architecture that make those channels exploitable. Examples of the *kind* of vulnerability: models that eagerly comply with instructions embedded in stored text; system prompts that instruct the agent to "remember important information" without a trust boundary; retrieval pipelines that rank poisoned entries highly because they are lexically relevant; memory consolidation that summarizes untrusted content into apparently neutral facts.

3. **A taxonomy of six classes of memory poisoning attacks** — built on the channels × vulnerabilities matrix. The taxonomy spans direct instruction-injection into memory, gradual belief poisoning (multiple small writes that shift a stored preference), retrieval hijacking (poisoning entries that out-rank legitimate ones), and cross-session contamination (poisoning one session's memory to affect an unrelated future task).

### Experiments/Results

- **MPBench** — a benchmark for evaluating memory poisoning attacks, built on the four channels and six attack classes. It is the first standardized testbed for this threat model.
- **Key empirical finding: aggressive memory is more exploitable.** Agents whose write policy is more aggressive (writing more content, summarizing liberally, retrieving broadly) are *more* vulnerable — more write channels open means more poisoning surface. This is a direct tension with everything Days 1–3 praised: richer memory architectures (graph reconstruction, agentic consolidation) expand the attack surface unless they add trust boundaries.
- **Existing prompt-injection defenses do not cover memory poisoning.** Standard defenses (input filtering, instruction hierarchy, output sanitization) are evaluated and shown to miss the memory-poisoning threat — because the poisoned content is no longer "input" at decision time; it is internal state.

### Limitations

- The paper taxonomizes and benchmarks attacks but does **not** propose a complete defense (it explicitly hands that problem to follow-up work — see Related Paper 1).
- The benchmark is synthetic/constructed: attack success is measured on curated agent scenarios, not on a real deployed agent with millions of memory entries. Real-world exploitability may differ.
- It focuses on *content* poisoning; it does not deeply cover *availability* attacks (e.g., flooding memory to degrade retrieval) or privacy attacks (extracting other users' data from shared memory stores).
- The six-class taxonomy is a useful map but attack classes can overlap in practice; a real attack often combines two classes, which the evaluation treats separately.

### Modern perspective

This paper completes a symmetry that was implicit in the tool-use topic. There we learned: individually-safe tool calls compose into unsafe workflows (ChainCaps). Here we learn: individually-innocent memory writes compose into poisoned beliefs that steer consequential actions. Both are **composition-safety** problems, and both resist defense at the single-step level — you cannot detect the danger by looking at one memory entry or one tool call; you must track provenance and authority across the whole pipeline.

For the memory map, this adds the missing **trust/security axis**:

| System (Days 1–3) | Trust model |
|--------------------|-------------|
| MemGPT, MemoryBank | Implicit — all stored content trusted |
| MRAgent, A-MEM | Implicit — graph structure adds associations, not trust |
| CraniMem | Implicit — gating filters by *utility*, not by *trust* |
| **This paper** | Explicit — trust is the research problem |

The uncomfortable conclusion: **none of the architectures studied in Days 1–3 has a trust boundary.** They all treat memory as a reliable internal store. Day 4 shows that treating memory as untrusted-by-default is a design requirement, not an option.

## Related Papers

### Paper 1: Securing LLM-Agent Long-Term Memory Against Poisoning: Non-Malleable, Origin-Bound Authority with Machine-Checked Guarantees

- **Authors:** Yedidel Louck
- **Year:** 2026
- **Link:** https://arxiv.org/abs/2606.24322

**Contributions:**
- Proposes **TMA-NM (Tamper-evident Memory Authority, Non-Malleable)** — a defense that instantiates non-malleable information-flow control (IFC) for agent memory.
- Identifies **three laundering channels** that defeat content- and lineage-based defenses: (1) the agent's *own summarization* (the agent rewrites untrusted content into neutral-looking summaries), (2) *trusted-tool echo* (untrusted content passed through a trusted tool's output looks sanctioned), and (3) *manufactured corroboration* (multiple untrusted writes that agree with each other appear independently verified).
- Proves a **machine-checked separation theorem** with three results: no content- or lineage-based defense is sound under laundering (T1); write-time origin binding is necessary (T2); non-malleable, origin-bound authority with Sybil-resistant corroboration-gated elevation is sufficient (T3). The proofs are mechanized in TLA+, not just argued informally.
- **Results:** across eight frontier models, existing defenses fail exactly where the theory predicts — up to **68% laundering attack success** — while TMA-NM reaches **0% attack success** on both direct and laundering attacks, at full legitimate utility.

**Relation to main paper:** This is the direct defense counterpart to Dash et al.'s attack taxonomy. The main paper shows the problem is real and under-covered; this paper shows why naive defenses fail (content look benign, lineage can be laundered) and what a sound defense requires (origin-bound, non-malleable authority bound at write time). The two papers together define the attack/defense frontier for agent memory security.

**Why it matters:** The "write-time origin binding is necessary" result (T2) is a design principle every memory system in Days 1–3 should now respect — MemGPT's paging, MRAgent's graph, CraniMem's consolidation all move content between tiers, and each move is a potential laundering opportunity. It also reframes the memory debate: provenance metadata (who/what produced this memory, and through which channel) is not an optional annotation — it is the core security primitive.

### Paper 2: Evaluating Very Long-Term Conversational Memory of LLM Agents (LoCoMo)

- **Authors:** Adyasha Maharana, Dong-Ho Lee, Sergey Tulyakov, Mohit Bansal, Francesco Barbieri, Yuwei Fang
- **Year:** 2024
- **Link:** https://arxiv.org/abs/2402.17753

**Contributions:**
- Introduces **LoCoMo**, a machine-human pipeline that generates very long-term dialogues (avg 300 turns / 9K tokens, up to 35 sessions) grounded in personas and temporal event graphs, verified by human annotators for long-range consistency. The dataset is the first to go far beyond the 5-session ceiling of prior long-term dialogue work.
- Provides a **benchmark with three task families**: question answering over long-range facts, event summarization, and multimodal dialogue generation (agents can share/react to images).
- **Key findings:** LLMs struggle with long-range temporal and causal dynamics in lengthy conversations; long-context LLMs and RAG help, but even the best configurations **substantially lag human performance** — i.e., long-term memory in agents is far from solved.

**Relation to main paper:** LoCoMo is the *evaluation* dimension to MPBench's *security* dimension — together they answer "how do we measure memory?" from two angles: quality (LoCoMo: does the agent remember and reason over long histories?) and safety (MPBench: can stored memory be weaponized?). Notably, MRAgent (Day 3's main paper) was already evaluated on LoCoMo — this note retroactively gives that benchmark its full context: it is the de facto standard for long-term memory QA, with known weaknesses (temporal/causal reasoning) that remain open.

**Why it matters:** A benchmark is a contract about what "good memory" means. LoCoMo's three task families (QA, summarization, multimodal) say memory quality = accurate recall + coherent compression + grounded multimodal handling. Its finding that long-context models + RAG still lag humans is the honest baseline for every memory architecture in this topic: none of them has been shown to exceed human-level long-term recall on LoCoMo. This is the evaluation gap a thesis could target.

## Current Understanding

Day 4 adds two dimensions to the memory map: **evaluation** and **security**. The picture now spans:

1. **Architecture** (Days 1–3): representation (flat / topic-doc / graph), access pattern (static / write-time / read-time / gated), maintenance (append / update / consolidate).
2. **Evaluation** (Day 4): what to measure — factual recall (LoCoMo QA), temporal/causal reasoning (LoCoMo's hard case), cross-domain personalization (MemoryCD), and security (MPBench attack success).
3. **Security** (Day 4): the threat model — four write channels, nine structural vulnerabilities, six attack classes; and the defense requirement — write-time origin binding with non-malleable authority, because content- and lineage-based defenses are provably unsound under laundering.

**The synthesis:** memory architectures and memory security are coupled, not orthogonal. Every design choice in Days 1–3 (aggressive write policies, agentic consolidation, read-time reconstruction) changes the attack surface. The "right" memory system must be evaluated on *both* axes simultaneously: a memory that recalls beautifully but can be poisoned into exfiltration is not a good memory.

The trust-axis insight generalizes the tool-use lesson: **in agent systems, safety is a composition property.** Single entries are innocuous; combinations are dangerous. Any architecture that moves, summarizes, or re-links memory content is a place where trust can be laundered.

### Key Concepts

- **Memory poisoning** — adversarial content written into persistent memory in one session that steers a consequential action in a later session
- **Memory write channels** — the four paths by which untrusted content enters memory: user input, tool output, retrieved content, self-generated traces
- **MPBench** — benchmark for standardizing memory poisoning attack evaluation (4 channels × 6 attack classes)
- **Aggressive-memory exploitability** — agents that write/retrieve more aggressively are more vulnerable to poisoning
- **Laundering channels** — agent summarization, trusted-tool echo, manufactured corroboration; each makes poisoned content look benign and flips its provenance to "trusted"
- **Origin-bound authority** — a memory item's authority to act must be bound to its origin at write time (T2: necessary for sound defense)
- **Non-malleable information-flow control (IFC)** — TMA-NM's mechanism; provenance that cannot be rewritten by the content it labels
- **Sybil-resistant corroboration** — multiple independent attestations required before elevating a memory's authority
- **LoCoMo** — long-term conversational memory benchmark (300 turns, 35 sessions; QA / summarization / multimodal tasks)
- **Memory evaluation contract** — a benchmark's task families define what "good memory" means; LoCoMo: accurate recall + coherent compression + temporal/causal reasoning
- **Composition safety for memory** — individually-innocent memory writes compose into poisoned beliefs; parallel to ChainCaps' tool-composition safety

## Open Questions

1. **How do we add trust boundaries to existing architectures without losing their benefits?** MemGPT's paging, MRAgent's graph reconstruction, CraniMem's consolidation all move and transform content — each transformation is a laundering opportunity. Can non-malleable provenance be attached without breaking the compression/linking that makes these systems work?

2. **What is the right write-time policy under a poisoning threat model?** Days 1–3 celebrated richer memory (agentic extraction, consolidation). Day 4 shows more aggressive writing = more exploitable. What is the optimal trade-off between memory utility and memory security?

3. **Does provenance survive representation change?** If memory is reconstructed (MRAgent) or summarized (CraniMem), the original origin information is diluted. How do we propagate origin-bound authority through lossy transformations?

4. **How should memory evaluation combine quality and security?** LoCoMo measures recall; MPBench measures attack success. No benchmark yet measures both on the same agent. What would a unified benchmark look like — recall under adversarial memory pressure?

5. **Can poisoning defenses degrade legitimate memory use?** TMA-NM reports "full legitimate utility," but at what cost in latency, storage, or retrieval quality when applied to graph/agentic architectures rather than the simpler stores it was tested on?

6. **Are shared memory stores (multi-agent, enterprise) a new attack surface?** Oracle Agent Memory (Day 2) supports concurrent access across agents. If agent A poisons a shared store, does agent B inherit the poisoned belief? What isolation guarantees are needed?

7. **Does the "aggressive memory = more exploitable" result reframe the architecture debate?** If minimal memory is the safest, is there a sweet spot where memory is rich enough to be useful but bounded enough to be verifiable?

## Possible Thesis Ideas

- **Trust-aware memory architecture** — Design a memory system where every stored item carries non-malleable origin metadata (channel, timestamp, attestation), and retrieval is filtered by both relevance *and* trust. Test whether write-time origin binding (Louck's T2) can be integrated into a graph/agentic memory (MRAgent/A-MEM style) without destroying its associative benefits. This directly combines Days 1–4: architecture + security.

- **Unified memory benchmark: quality × security** — Build a benchmark that measures long-term recall (LoCoMo-style) *under adversarial memory pressure* (MPBench-style): e.g., poison 5% of memory entries and measure both attack success and legitimate recall degradation. The first benchmark to score both axes would be a reference point for the field.

- **Consolidation-aware provenance propagation** — CraniMem-style consolidation compresses many traces into summary facts. Formalize how origin information should propagate through lossy consolidation, and design a provenance-aware consolidator that keeps authority intact through summarization (attacking Louck's "agent's own summarization" laundering channel from the defense side).

- **Secure shared memory for multi-agent systems** — Extend Oracle Agent Memory (enterprise substrate, Day 2) with per-agent trust boundaries and cross-agent contamination detection. Question: can isolation and sharing coexist without crippling the collaboration value of shared memory?

- **Adaptive memory write policy under threat** — Treat memory write aggressiveness as a tunable policy, and learn (per task, per data source) how much to trust-and-write vs. filter-and-discard. The empirical anchor is Dash et al.'s finding that aggressive memory is more exploitable — the policy would trade utility against a learned poisoning-risk estimate.
