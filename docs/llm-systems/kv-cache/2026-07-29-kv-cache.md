## Today's Question

Beyond quantization (compressing each KV entry) and eviction (removing entries entirely), how do offloading systems move KV cache across GPU, CPU, and storage tiers to support long-context inference? Can these three pillars be unified into a holistic management strategy?

## Main Paper

### Metadata

- **Title:** ShadowKV: KV Cache in Shadows for High-Throughput Long-Context LLM Inference
- **Authors:** Hanshi Sun, Li-Wen Chang, Wenlei Bao, Size Zheng, Ningxin Zheng, Xin Liu, Harry Dong, Yuejie Chi, Beidi Chen
- **Year:** 2024
- **Venue:** NeurIPS 2024 / arXiv:2410.21465
- **Link:** https://arxiv.org/abs/2410.21465

### Why this paper?

We've covered quantization (Day 1 — KIVI) and eviction (Day 2 — Make Each Token Count). The third pillar of KV cache management is **offloading** — moving cache entries to cheaper tiers (CPU DRAM, SSD) when GPU memory runs out. ShadowKV is the most interesting recent system in this direction because it doesn't just offload naively: it uses a low-rank decomposition of the key cache to store only the essential information, combined with an accurate KV selection strategy that reconstructs the minimal sparse KV pairs on-the-fly.

### Core Problem

Long-context LLM inference faces a throughput bottleneck: as sequence length grows, the KV cache consumes more GPU memory, reducing the maximum batch size. Even with dynamic sparse attention that skips some KV entries, the GPU memory footprint remains large. Naive CPU offloading (move everything to CPU, fetch on demand) adds significant decoding latency due to PCIe transfer overhead.

### Main Idea

ShadowKV makes a key observation: the **key cache is low-rank** (can be compressed via SVD), while the **value cache is not compressible in the same way**. So it stores only the low-rank key cache on GPU (compressed via truncated SVD to rank 64), while offloading the value cache to CPU memory. During decoding, it selects the most important KV pairs based on the low-rank keys and fetches only those values from CPU — a form of informed sparsity that reconstructs "minimal sparse KV pairs on-the-fly."

This is different from naive offloading because:

1. **Low-rank key storage** on GPU: storing keys in SVD-compressed form (rank 64) uses a fraction of the original memory, so most keys are effectively "always resident" in compressed form.
2. **Accurate KV selection**: the compressed keys still capture enough attention information to determine which positions matter. Only the value cache entries for selected positions need to be fetched from CPU.
3. **On-the-fly reconstruction**: the decompression and sparse KV assembly happens just-in-time for each decoding step.

### Technical Details

- **Batch processing per layer:** processes attention layer-by-layer rather than token-by-token, creating opportunities for batched CPU→GPU transfers of value cache entries.
- **SVD rank selection:** rank 64 provides the best accuracy-efficiency tradeoff across Llama-3.1-8B, GLM-4-9B-1M, and other models.
- **Sparsity ratio:** ShadowKV achieves 5-25% KV pair retention while maintaining accuracy (higher retention for longer contexts that need more tokens).
- **Hardware support:** Designed for A100 80GB, scales to 1M context on single GPU.
- **Implementation:** Built on PyTorch with custom CUDA kernels for low-rank projection and sparse KV assembly. GitHub: https://github.com/bytedance/ShadowKV

### Experiments / Results

| Metric | ShadowKV vs. baseline |
|--------|----------------------|
| Max batch size | Up to 6× larger |
| Throughput | Up to 3.04× on A100 |
| Accuracy (RULER, LongBench, Needle) | Comparable to full KV |
| Inference quality | Matches full-cache across multiple benchmarks |

Models tested: Llama-3.1-8B, Llama-3-8B-1M, GLM-4-9B-1M, Yi-9B-200K, Phi-3-Mini-128K, Qwen2-7B-128K.

### Limitations

- **Only tested on small-to-medium models** (up to 9B params). Scaling to 70B+ models would require even more aggressive compression or multi-GPU offloading.
- **SVD rank is static (rank 64).** A dynamic rank selection per-layer or per-position could improve the accuracy-offloading tradeoff.
- **Focuses on single GPU inference.** Multi-GPU disaggregated settings (where prefill and decode run on different machines) add a network transfer dimension not addressed here.
- **Offloads only value cache.** Keys benefit from low-rank compression, but the approach assumes keys are the bottleneck. Some models with different attention patterns might benefit from symmetric treatment.

### Research takeaway

ShadowKV demonstrates that **KV cache offloading doesn't have to be "move everything and pay the latency."** By exploiting the low-rank structure of the key cache, we can keep the essential attention information GPU-resident and only pay PCIe bandwidth for the value cache entries that actually matter. This is analogous to how KIVI exploits asymmetric quantization (keys quantized differently from values) — there is something fundamental about the key-value asymmetry in transformer attention that systems can exploit.

### Modern perspective

ShadowKV (Oct 2024) sits between FlexGen (2023, foundational offloading) and KVDrive (2026, holistic multi-tier). It's the first system to combine **mathematical insight** (key cache is low-rank) with **system engineering** (batched value fetches, on-the-fly reconstruction) for KV cache offloading. Compared to pure eviction approaches (Day 2), it keeps all information available (just in compressed/deferred form) rather than discarding it.

## Related Papers

### Paper 1: FlexGen — Canonical Offloading

- **Title:** FlexGen: High-Throughput Generative Inference of Large Language Models with a Single GPU
- **Authors:** Ying Sheng, Lianmin Zheng, Binhang Yuan, Zhuohan Li, Max Ryabinin, Daniel Y. Fu, Zhiqiang Xie, Beidi Chen, Clark Barrett, Joseph E. Gonzalez, Percy Liang, Christopher Ré, Ion Stoica, Ce Zhang
- **Year:** 2023
- **Venue:** ICML 2023 / arXiv:2303.06865
- **Link:** https://arxiv.org/abs/2303.06865

**Contribution:** FlexGen pioneered the idea that LLM inference can run on a single commodity GPU by aggregating memory from GPU, CPU, and disk. It formulates tensor placement as a linear programming problem, searching for efficient patterns to store and access tensors across three tiers. It also compresses weights and attention cache to 4 bits.

**Relation to main paper:** ShadowKV inherits FlexGen's core philosophy (offload to survive limited GPU memory) but replaces the naive "move everything" strategy with a smarter selective approach based on the key cache's low-rank property. FlexGen proved offloading is feasible; ShadowKV made it efficient enough for real-time use.

**Why it matters:** FlexGen achieved the first 1 token/s generation on OPT-175B with a single 16GB GPU (batch size 144) — a landmark result that showed offloading-systems could work for latency-insensitive tasks. Its LP-based tensor placement is still a useful baseline.

### Paper 2: KVDrive — Holistic Multi-Tier Management

- **Title:** KVDrive: A Holistic Multi-Tier KV Cache Management System for Long-Context LLM Inference
- **Authors:** Jian Lin, Jiazhi Mi, Zicong Hong, Haodong Wang, Qianli Liu, Haodyue Zhang, Peng Li, Song Guo
- **Year:** 2026
- **Venue:** arXiv:2605.18071
- **Link:** https://arxiv.org/abs/2605.18071

**Contribution:** KVDrive tackles KV cache management across **three tiers** (GPU, host DRAM, SSD) with holistic orchestration of cache placement, pipeline scheduling, and cross-tier coordination. Unlike ShadowKV's clever but single-focus approach, KVDrive jointly manages eviction, offloading, and compression decisions based on attention behavior to maximize reuse.

**Relation to main paper:** KVDrive is the next evolution — it argues that **sparsity alone has a ceiling** and we need system-level multi-tier orchestration. ShadowKV pushes sparsity as far as it can go (5-25% retention); KVDrive says that's not enough for production 1M+ context workloads and complements it with pipeline scheduling that overlaps I/O with compute.

**Why it matters:** KVDrive shows the integration of all three KV cache pillars (quantization, eviction, offloading) into a single system. It achieves 1.74× higher throughput than state-of-the-art works. This is the direction for thesis-level work: unified, adaptive, tier-aware KV cache management.

## Current Understanding

The KV cache management landscape now has **three pillars** after today's reading:

1. **Quantization** (Day 1 — KIVI): Compress each KV entry to fewer bits. Asymmetric quantization (per-channel K, per-token V) works well. Achieves 2-4× memory reduction.

2. **Eviction** (Day 2 — Make Each Token Count, StreamingLLM): Remove entries permanently based on importance. Attention sinks must be preserved. Eviction-aware training helps. Achieves 4-10× reduction.

3. **Offloading** (Day 3 — ShadowKV, FlexGen, KVDrive): Move entries to cheaper tiers without discarding them. Low-rank key compression + selective value fetch is the smart approach. Multi-tier orchestration (GPU→DRAM→SSD) is the next step.

The key insight connecting all three: **KV cache is not monolithic.** Keys and values have different compressibility characteristics. Different layers have different sensitivity to precision. Different attention heads have different importance profiles. A unified system must exploit all these asymmetries.

The three pillars are **complementary**, not competing. A production system should:
- Quantize KV entries (KIVI-style) to reduce the per-entry footprint
- Evict unimportant entries (Make Each Token Count-style) to reduce the entry count
- Offload remaining entries to CPU/SSD (ShadowKV/KVDrive-style) when GPU memory is exhausted

The gap: no existing system combines all three in a learned, adaptive way. KIVI does quantization only. Make Each Token Count does eviction only. ShadowKV does smart offloading with low-rank keys. KVDrive does multi-tier orchestration but doesn't incorporate learned quantization. **Combining all three with a learned policy is an open research opportunity.**

## Key Concepts

- **KV cache offloading:** Moving KV entries to CPU DRAM or SSD when GPU memory is full
- **Low-rank key cache:** The observation that the key cache matrix has low effective rank, enabling SVD compression
- **On-the-fly sparse reconstruction:** Building the minimal sparse KV set from compressed storage at each decoding step
- **PCIe bandwidth bottleneck:** The primary latency constraint for CPU→GPU KV transfers during offloading
- **Multi-tier cache hierarchy:** GPU HBM (fast, small) → CPU DRAM (medium, medium) → SSD (slow, large)
- **Pipeline scheduling:** Overlapping I/O (CPU→GPU transfers) with compute (attention, MLP) to hide latency
- **Joint compression-eviction-offloading:** The emerging unified view of KV cache management as a single optimization problem

## Open Questions

- **Can low-rank key compression be combined with KIVI's asymmetric quantization?** The key cache is both low-rank and amenable to quantization — a combined approach could yield multiplicative savings.
- **What is the optimal tier placement policy?** Which layers/heads should be GPU-resident, which on CPU, which on SSD? KVDrive starts answering this but the policy is heuristic-driven, not learned.
- **How does offloading interact with disaggregated inference?** In a prefill/decode disaggregated system, the KV cache must be transferred over the network. Does offloading to CPU help or hurt the disaggregation pipeline?
- **For agent workloads (tool-interleaved, short turns), does offloading make sense?** Agent conversations are short per-turn but accumulate context over many turns. The offloading benefit is less clear for bursty, low-latency agent calls.
- **Can we dynamically adapt the offloading policy based on SLO requirements?** Different requests have different latency requirements — a unified system should trade off offloading aggressiveness per-request.

## Possible Thesis Ideas

- **Unified KV cache manager across all three pillars:** A learned policy that jointly decides (a) which entries to quantize and at what bit-width, (b) which to evict, and (c) which to offload and to what tier. This would be the first end-to-end system that composes all three techniques with an optimization objective (e.g., maximizing goodput under memory SLOs). The state space is large but learnable via RL or offline optimization.

- **Low-rank + quantized hybrid KV cache:** Combine ShadowKV's low-rank key compression with KIVI-style asymmetric value quantization. The hypothesis: keys are compressible via SVD, values are compressible via quantization — together they could achieve 10-20× total KV cache reduction while keeping accuracy.

- **Agent-aware KV cache lifecycle management:** Design an offloading/eviction policy specifically for agent workloads where the same KV cache is reused across tool calls. Unlike document inference (one long sequence), agent conversations have high-value tokens (system prompts, tool definitions) and low-value tokens (intermediate thought tokens) — a tier-aware policy could keep high-value tokens GPU-resident.

- **Cross-tier pipeline scheduling for disaggregated serving:** In a disaggregated setting (prefill on one machine, decode on another), KV cache transfer over the network is the bottleneck. Can we combine ShadowKV-style low-rank compression with pipeline scheduling to hide network transfer latency?
